# 沙箱运维管家（sandbox-project-ops）

> \这是中文解释：本技能 frontmatter 中的 description 偏长系历史原因（2026-08 多轮会话逐步追加触发条件所致），为避免触发回归本次不做收敛，留待后续大版本统一精简。

在沙箱中维护**跨多个会话持续迭代**的项目（用户会给出版本号式指令，如"继续自主迭代 v68.x"）时，先执行本规程再动手改代码。

## 环境事实（2026-08 多次会话验证）

- `shell` 工具以 **root (uid 0)** 运行；`ipython` 工具以 **kimi (uid 999)** 运行。两者写入 `<输出区>` 下的同一项目目录时互相制造权限问题。
- 沙箱在会话之间会**重置**：pip 装的包（pytest 等）和项目的 `.git` 目录会丢失，但 `<输出区>` 下的项目文件保留。
- 症状：ipython / write_file 报 `Permission denied`；`pytest` 或 `git` 突然 "command not found" 或 `.git` 消失；git 报 `fatal: not in a git directory` / dubious ownership（root 操作 uid 999 拥有的仓库）。
- **工具网关会掐断长调用**：单次 shell/ipython 调用内含 `sleep` ≥60~90s 或同步等长任务时，大概率返回 `504 Gateway Timeout` / `deadline_exceeded: context deadline exceeded`（两种报错同族，都是网关杀调用；2026-08-15~20 单会话 504 出现 43 次，2026-08-21/22 会话再出现 43 次 504 + 3 次 deadline_exceeded，几乎全部是带长 sleep 的调用；≤30s 的短调用稳定成功）。失败是非确定性的——长 sleep 偶尔也能返回，不能因此侥幸。
- **shell 每轮调用都是全新会话，跨轮等待守护进程必须托管在 IPython 内核**（2026-09-04 lark-cli 授权流程实测）：shell 后台拉起的等待进程会随该次调用结束被回收，`/tmp` 在会话边界也会被清空——上一轮发好的授权链接因此失效。区分两种后台：**会话内短后台**（pytest 跑批+短调用轮询，上文跑法不变，可行）vs **跨轮等待守护**（OAuth/CLI configure 等用户动作等待，分钟~小时级，可能跨越压缩/会话边界）——后者一律用 `subprocess.Popen` 从 IPython 内核启动（内核跨调用持久），每轮先确认 PID 存活再依赖其结果；关键状态（配置路径、chat_id、授权中间件）持久化到 `<输出区>` 或 `<上传区>`，**不放 /tmp**；授权链接/二维码有有效期，失效即重发并显式宣告旧件作废，同时预置降级方案（如用户手动复制 App Secret 走 stdin 非交互落盘）。
- **本项目测试套件很慢**：2026-08-21 实测即使 `-k` 过滤后（4 passed / 553 deselected）也要 311s。全量套件必然超过单次调用时限，**一律从第一次就后台起跑**，不要先前台试一次再转后台。

## Workflow

0. **先读项目索引再动手（接手既有项目时必做）**：`<输出区>` 根目录是多会话共享的知识库。研究/迭代前先用一个短调用盘点：`ls <输出区>/` + 读 `MASTER_INDEX_*主归档索引.md`（若存在）+ 全部 `【必读】*` 文件 + 相关 `archive_<主题>/00_INDEX.md`。【必读】文件是特别标注的硬结论（如某校装置报废核查），后续产出不得与其矛盾；发现矛盾时主动修改旧文件而不是各说各话（用户 2026-08-21 明确要求"修改存在矛盾的文件"）。跳过这一步会被用户打回（2026-08-21 用户原话："请您直接读取，现在根目录下应该是已经必读的文件"）。
1. **会话开始（接手既有项目时）**：运行 `scripts/session_bootstrap.sh <项目目录>`，一次性完成：
   - `chown -R 999:999 <项目目录>`（修权限，两个工具都能写）；
   - pytest 缺失则 `pip install -q pytest`；
   - `.git` 缺失或失效则 `git config --global --add safe.directory <项目目录>` + `git init` + 配置 user.name/user.email（并按项目文档重建 pre-commit hook），最后用 `git rev-parse --git-dir` 验证仓库真的可用。
2. **每次用 shell 往项目目录写文件后**：立刻 `chown -R 999:999 <项目目录>`，不要等 ipython 报 Permission denied 再修。修一次只管当下，后续 shell 写入又会复发。shell 直接写到 `<输出区>` 根下的交付文件（如排名报告 .md）也要一并 chown，否则 ipython 侧同样写不动。
3. **跑长测试套件（红线，技能已加载也不许破例）**：用 `python3 -m pytest tests/ -p no:cacheprovider --tb=no -q > /tmp/run.txt 2>&1 &` 后台启动后**立即返回**，然后用一系列**短调用**轮询：`grep -aE "[0-9]+ passed|[0-9]+ failed" /tmp/run.txt` 和 `ps aux | grep -c "[p]ytest"`（strip ANSI 色码：`sed 's/\x1b\[[0-9;]*m//g'`）。**不要在任何单次调用里 `sleep` ≥60s 等结果**——网关会 504 / deadline_exceeded，任务白等；sleep ≤30s 的短调用可接受。2026-08-21/22 会话中，用户已在会话内显式加载本技能，后续仍发出 18 次 sleep 等待（其中 17 次 ≥60s），2 次被打死——加载技能≠遵守，每次想 sleep 长等时先停手。
4. **ipython 内核重置后**：症状是项目 import 突然 ModuleNotFoundError 或相对路径 FileNotFoundError（内核可能因 504 等原因被重启，丢失 sys.path/cwd）。重跑前置：`sys.path.insert(0, '<项目目录>')` + `os.chdir('<项目目录>')` 再 import。
5. **交付前硬门槛**：pytest 必须全绿、项目自带的内容/审计脚本（如 pre-commit 核查）必须退出码 0，才可向用户报告完成。版本号（如 facade `__version__`）与其测试断言必须同批更新。
6. **隐私红线**：用户长期项目禁止把证件号、准考证号、家庭成员姓名等敏感信息写入任何产出文件或数据库；一律用 generic 指代（父亲/母亲等）。

## 跨会话文档归档约定（2026-08-21/22 六个会话验证）

用户把 `<输出区>` 根目录当作评分系统与其他会话共用的知识库，频繁要求"写入根目录并维护""归档并自主合并命名，方便主程序评分系统调用及识别""供其他对话调用"。约定如下：

- **入口索引**：根目录维护 `MASTER_INDEX_*_主归档索引.md`（2026-08-21 创建，后续 4 个会话复用）。索引按使用场景组织：机器调用（评分系统读的路径+格式+版本表）、人工决策（决策问题→推荐文档）、跨对话引用（`sandbox://<输出区>/完整文件名` 链接格式）。产出新文档后必须回写索引；索引缺失时主动补建。
- **【必读】标注**：对"查询到 X 时不能出现任何偏差"的硬结论，在根目录建 `【必读】<主题>_专项核查标注.md`（2026-08-21 南华装置报废案例）。所有后续产出与必读文件保持一致；发现矛盾时修改旧的矛盾文件，而不是并存两套结论。
- **专题归档结构**：一个研究主题收敛后归档为 `archive_<主题>/`，固定子目录：`01_raw_research`（原始调研）、`02_critical_reflection`（批判反思）、`03_technical_template`（技术模板）、`04_paradigm_document`（范式文档）、`05_metadata`（archive_metadata.json）、`06_scoring_system_bridge`（评分系统对接），根部配 `00_INDEX.md` + `MANIFEST.md` + `TREE.md`（2026-08-21 氢能、中外合作两个专题均按此结构）。
- **版本与机读配置**：范式文档按版本迭代（V1.0→V1.2→…→收敛版），每个评分范式配套一份机器可读 JSON 参数配置（如 `高校跨省就业评估参数配置_V2.3.json`、根目录的 `择校决策系统_评分参数_v10.0.json`）供主程序直接加载；改范式必同步改 JSON 配置。
- **状态追踪文档**：用户会要求"写入根目录并维护"的活文档（如 `中外合作项目状态追踪_2026.md`）——同类后续信息更新进同一文件，不要每次新建。

## 「自主推进排期」执行规程（2026-08-22/23/24 约 10 个会话验证）

用户最高频指令是"请您自主推进相关排期""继续推进排期""排期建议"。这里的"排期"**不是软件 Sprint**——是用户个人研究/申请项目群（评分系统、核聚变调研、导师套磁、医疗事故评判、出行规划等）的跨会话任务调度。规程：

1. **先盘点再排**：读根目录 MASTER_INDEX → 读各项目状态追踪/排期文档（如 `自主迭代解构_vX.Y_可执行排期与行动矩阵.md`、`*状态追踪_2026.md`、`排期推进状态看板.json`）→ 列出所有 pending 线程及各自最新版本号。
2. **产出有序可执行清单**：每项含「动作 + 对应文档/skill + 验收标准 + 预计耗时」，按依赖与截止日期排序；标注哪些项本会话内可直接执行、哪些需用户线下动作（发邮件、缴费、打电话）。
3. **当会话直接执行首项**：排期不是纯规划——排序第一的可在沙箱内完成的项（调研、核查、写文档、跑脚本），本会话内就开始做并落盘。
4. **回写状态**：执行结果更新进同一状态追踪文档（不新建同类文件），版本号**诚实递增**（用户明确要求"诚实更新相关版本号，避免过度夸大跨越大版本号"）。
5. **禁止套用不适配模板**：不要用 iteration-planner（软件 Sprint 规划，Velocity/Story Point 体系）或 audience-adapter（向上汇报）回应此类请求——2026-08-22/23 实测套用 Sprint 模板产出"把用户当 PM 排 Story"的计划，与用户真实意图（个人项目群调度）完全错位。

## Pitfalls

- **聊天内版本空转、零落盘（最严重失败模式，2026-08-23 实测）**：用户要求把 AAPP 协议"蒸馏成机器可读 skill"，agent 在单会话内从 v5.0 一路"迭代"到 v3.13、产出 20+ 版聊天文本，**全程未写一个文件**，用户被迫重复同一指令 15+ 次。规则：任何"迭代/收敛/蒸馏"请求，每一轮都必须落盘（文件 + 版本号），最后一轮必须是可交付产物（.skill 包/文档文件），不是聊天文本。
- **技能装错目录导致不持久**：在 `/app/.agents/skills/`（平台目录）里新建 skill，会话结束即丢失（2026-08-22 amap-travel-skill 两次构建均随沙箱销毁）。用户自建 skill 一律写入 `<技能安装位>/`；且**每完成一个文件立即落盘**——工具预算耗尽（"工具调用预算已耗尽"）会中断会话，先写核心文件（SKILL.md → 脚本 → 参考文档），别攒到最后一次性写。
- **引用其他会话产物前不核验存在性**：2026-08-24 会话引用"64 案例数据集（A/B 级 76/24）"时发现其未持久化到当前环境——不同会话的 output 目录不一定互相可见。引用跨会话产物前先 `ls` 核验；不存在就如实报告并从根目录索引能找到的最新版本重建，不要把记忆里的统计口径当既有事实引用。
- **找不到文档时预生成"推断框架"冒充**：2026-08-23 用户要求按 `自主迭代解构_v4.0` 推进排期，agent 未找到该文件就先输出一份"推断框架"再要求用户上传。规则：先全盘检索（`ls` 根目录 + grep 关键词），确实缺失时直接说明"未找到，请上传或确认用 v5.0 替代"，**不要先编一份推测内容**——用户会把它误认为原文件。
- **只在 ipython 里写、忘了 shell 写过**：root 写入的文件 ipython 改不动；表现为 write_file/edit_file 失败。先 chown 再重试，别重建文件。第一次 PermissionError 就该跑 bootstrap 一次修全，不要每次 ad-hoc chown（2026-08-15~20 会话中复发 ≥5 次）。
- **假设 pytest/git 还在**：跨会话必先 bootstrap，否则跑到一半才发现环境没了。
- **`git init -q && git config ...` 长链掩盖失败**：`git init -q` 在所有权异常时可静默失败，后续命令报 `fatal: not in a git directory`（2026-08-19 实测）。先 `git config --global --add safe.directory <项目目录>`，再 init，最后 `git rev-parse --git-dir` 验证。
- **在调用里 sleep 等长任务**：`sleep` 90~250s 的 shell 调用全部 504（2026-08-15~20 实测 20+ 次）；2026-08-21/22 复发（43 次 504 + 3 次 `deadline_exceeded`，含技能已在会话内加载之后仍发出的 sleep 90~280s 调用）。改为后台写日志 + 短调用轮询。
- **从零开始研究而不先读索引**：不读 MASTER_INDEX /【必读】/ 00_INDEX 就开查，导致重复劳动或与既有硬结论矛盾，被用户纠正（2026-08-21）。接手先盘点根目录。
- **新文档散落根目录不回写索引**：用户多次要求"归档并合并命名，方便评分系统调用"；产出后不更新 MASTER_INDEX、不同步 JSON 参数配置，等于没交付。
- **ipython 内核重启后沿用旧假设**：sys.path/cwd 丢失导致 import/读数据文件失败，先补前置再重试，不要误判为项目文件损坏。
- **没跑测试就报"已交付"**：用户以 pytest 全绿 + git commit 哈希作为交付标准；跳过会直接被打回。
- **用正则改写测试文件**：项目测试断言含版本号/参数计数，改动务必只替换目标行并立即跑测试验证。

- **跨轮等待进程放 shell 后台**：等待用户完成授权（lark-cli configure 类）的进程放 shell 后台，调用一结束进程即死、`/tmp` 被清空，授权链接静默失效（2026-09-04 实测一轮）。改法：从 IPython 内核 `subprocess.Popen` 启动等待进程并每轮确认存活；状态文件落 `<输出区>`；链接失效就重发新码并宣告旧码作废。
- **CLI 配置家目录的双 uid 陷阱**：lark-cli 等 CLI 的配置写在「执行侧」的家目录——内核侧=kimi（`/home/kimi/.lark-cli`）、shell 侧=root（`/root/.lark-cli`）。在内核侧完成 configure 后，shell 侧调用仍报未配置（反之亦然）。改法：全链路固定走同一侧（推荐内核通道），或显式把配置目录桥接到另一侧并验证，别假设两侧共享。

## Resources

- `scripts/session_bootstrap.sh <项目目录>`：会话开始环境自检+修复（权限/pytest/git safe.directory/git 仓库有效性）。幂等，可重复运行。用 `sh scripts/session_bootstrap.sh <项目目录>` 调用（直接执行可能因挂载/权限被拒）。

## 平台版本甲 快速低配模式与相关技能对接

> \这是中文解释：本节为 2026-08-24 整合迭代新增，用于在工具预算受限/上下文紧张的"快速低配模式"下给出降规程与相关技能对接指引，属增量追加，不影响上文既有规程。

- **快速低配模式（工具预算受限/上下文紧张）**：当会话进入快速低配模式时，本规程可降级执行——优先保落盘与版本诚实，精简非必要的环境巡检与轮询频次。降规程的具体阈值、降级的迭代收敛规则由 extension skill **iteration-convergence-ops** 承载，路径：`<输出区>/skills/iteration-convergence-ops`（若该路径产物在当前会话尚未存在，则该部分"将由 iteration-convergence-ops 技能承载"，先按本规程默认完整流程执行）。
- **技能全量导入与跨会话衔接**：涉及技能包的全量导入、跨会话工作流衔接与交接协议时，对接 **cross-session-workflow-bridge** 技能（同目录下 `cross-session-workflow-bridge/`），按其 handoff_protocol 执行衔接。
