# 摄取规程（fetch-protocol）

> v1.0 ｜ 2026-08-25 ｜ 修改人：Orchestrator（Kimi K3）

## §1 直取通道（实测基线）
- 通道阶梯（v1.1 修订，eval-1 实战）：
  1. `web_open_url`（正文主通道，实测 6/6 成功）；
  2. **辅助元数据通道 M**：curl/requests 拉同一公开 HTML，解析内联 JS 变量（`var ct` 时间戳→pub_date、`ghid`→account_id、`nickname`、`author`、`msg_title` 交叉、`js_content` 全文比对→截断/图片检测）。合规四前提：仅限用户提供的公开 URL、低频、不伪造 cookie/签名、遇墙即停——禁止 IP 轮换/打码/appmsg_token 类逆向（红线，与 interfaces §3 一致）；
  3. `browser_visit`（hub 页递归专用）；
  4. 全失败留痕跳过。
- 失败形态登记表：`环境异常/验证码墙（wappoc_appmsgcaptcha，browser 通道常见——遇墙≠元数据不可得，转通道 M）/需登录/付费墙/已删除/长文截断`。
- 实测：mp.weixin.qq.com 直取 6/6 成功（2026-08-24/25 两轮）；browser 通道遇验证码墙 0/1；通道 M 补 pub_date/account_id 3/3（baseline 实证）。
- **hub 页递归**：目录型文章（如《区域产业》hub）正文含子文章标题但 web_open_url 不返回其 URL——须用 `browser_visit` 打开后 `browser_find`/元素提取拿 href，或请用户补链接；递归深度 ≤2 层，防爆炸。
- 失败形态登记：环境异常/需验证/付费墙/已删除——写入批次报告 failed 段，禁止编造正文。

## §2 批次节奏
- 每批 ≤10 条链接；批间可配 `add_cron_job` 定时续批（用户要求持续推进时）。
- 大批次（>30）拆多个摄取子代理并行（每代理一批，互不依赖）。

## §3 元认知收敛纪律（摄取质量的迭代自检）
每批结束后回答四个问题（写入批次报告「元认知自检」节）：
1. 本批获取率？失败形态分布？
2. 标题/日期/来源号三元组（=七元组的摄取时子集）提取完整率？（pub_date 缺失→下批启用通道 M）（缺失→下批调整提取策略）
3. 正文截断/乱码检测？（长文截断边界未验证——>2万字文章须抽查尾部完整性）
4. hub 递归命中率？（未命中→改浏览器通道或请用户补链）
连续两批四项全绿 → 该来源通道标记「稳定」；出现系统性失败 → 降通道并留痕。

## §4 准公众号范式（多次少量链接的累计协议）
用户分批投喂链接时：
1. 每批到达即入 `inbox.jsonl`（link/到达时间/批次号）；
2. 达到阈值（默认 ≥8 条或用户说"先处理"）触发摄取批次；
3. 每篇归档后回执一行：标题|日期|信源级|归档路径——模拟"公众号推送"体验；
4. 用户说"停"则封存批次并出阶段报告；
5. **系列触发**（v1.1）：同 account_id ≥2 篇且带系列标签（如【行研】/【区域】）→ 交接段产出"系列监测建议"。
- 元数据补齐后，pub_date 为 unknown 的行应回刷指针 CSV（留痕修改人+日期）。

## §5 批量导入格式
- 文本：每行一个链接或文章短码（`/s/<code>` 的 code 段），脚本自动补全前缀+去重+过滤非 mp.weixin.qq.com 域。
- JSON：`[{"url":"...","note":"可选备注"}]`。
- scripts/link_dedup.py 处理两种输入，输出规范清单+重复报告。
